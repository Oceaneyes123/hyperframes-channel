F1 · The question7.8s

Your Windows laptop has no network access. How does it reach your company's domain? Four different services make that happen.

Situation: five objects on one stage. Action: the cabling is drawn, then each service is named in turn. Consequence: the opening state shows a laptop with no address inside a populated corporate network.

F2 · Plugging in9.4s

First the laptop connects, by cable or by Wi-Fi. It is on the network now, but it still has no address of its own.

Situation: the laptop is physically linked. Action: the cable strokes on and the access point lights. Consequence: the configuration plate underneath stays empty, so 'connected' is visibly not 'configured'.

F3 · Discover10.2s

So it asks. DHCP Discover goes out as a broadcast across the local network. Is there a DHCP server here?

Situation: the laptop has no address. Action: a dashed path is drawn because the destination is unknown, and a DISCOVER token travels it. Consequence: the DHCP server lights up, proving the broadcast reached it.

F4 · Offer8.2s

A DHCP server answers with an offer, an address it is willing to lend before anything is confirmed.

Situation: the server has the request. Action: the OFFER token retraces the established route. Consequence: the laptop's plate gains an address in amber, marked OFFERED — visibly provisional.

F5 · Request6.2s

The laptop replies with a request, asking that server to keep that exact offer for it.

Situation: an offer is on the plate. Action: a REQUEST token travels the established route to the server. Consequence: the server lights as the chosen one; nothing is confirmed yet.

F6 · Acknowledge5.5s

The server acknowledges. The lease is committed, and the laptop has working network settings.

Situation: the server was asked. Action: the ACK token returns and the plate fills row by row. Consequence: the plate is complete - address, gateway and DNS - and an explicit LEASE ACTIVE mark resolves the exchange.

F7 · The configuration bundle9.0s

DHCP delivered four things: an IP address, a subnet mask, a default gateway, and a DNS server.

Situation: DORA is complete. Action: four values list in the free left band one at a time. Consequence: the DNS row changes to the discovery color, marking which of the four the next scenes depend on.

F8 · Why the DNS setting matters10.5s

In a domain, that last setting matters most. A wrong DNS server still lets you browse the internet, but you will never find the domain.

Situation: the plate's DNS value is the link to the directory. Action: a query token runs to DNS, DNS lights, then the Domain Controller lights. Consequence: a green DOMAIN FOUND resolves the chain and an amber NO DOMAIN states the failure case.

F9 · The discovery question8.2s

So the laptop asks DNS a direct question: where is a domain controller for the domain corp dot example?

Situation: the client has a domain name, not an address. Action: a query token travels to DNS. Consequence: DNS lights as the service that holds the answer — no broadcast is drawn at any point.

F10 · The service record8.6s

DNS answers with a service record, an S R V record, that names the domain controller's host and its address.

Situation: DNS was asked. Action: the SRV name is shown, a route is drawn to the directory, and an SRV token carries the answer. Consequence: two result rows give the controller's host and address.

F11 · Contacting the Domain Controller8.2s

With a name and an address, the laptop now contacts that domain controller directly, to confirm it is alive and reachable.

Situation: the client holds a host and an address. Action: a direct route is drawn and a contact token travels it. Consequence: the controller glows and a green DC IS ALIVE resolves the discovery.

F12 · Domain sign-in9.0s

The user signs in. The identity travels to the domain controller, Kerberos carries the authentication, and the account is checked in Active Directory.

Situation: the client can reach the controller. Action: an identity token travels to it, a route is drawn into the directory, and an account check follows. Consequence: a green SIGNED IN result.

F13 · A different kind of network9.8s

That is the normal path. But some corporate networks will not hand out a working port at all until the device proves who it is.

Situation: the normal path has worked so far. Action: a port lock is drawn on the switch, the way onward is shown blocked, and NPS appears. Consequence: the viewer sees a network where access itself is gated.

F14 · The three roles11.7s

That is where 802.1X comes in. The laptop is the supplicant. The switch or access point is the authenticator. And NPS is the RADIUS server behind it.

Situation: a gated port. Action: three role rows name each party in narration order, then an identity token travels the chain. Consequence: the chain laptop → switch → NPS → directory is on screen with every role labelled.

F15 · Who sends the RADIUS request10.9s

The laptop never talks to NPS. The switch or access point sends the RADIUS request on its behalf, because that is the device holding the port.

Situation: the three roles are known. Action: the wrong path is drawn and struck out, then the real switch-to-NPS path is drawn and a RADIUS token travels it. Consequence: an explicit NOT FROM DEVICE row fixes the architecture.

F16 · NPS decides8.2s

NPS receives the request, matches it against its connection and network policies, and checks the identity against Active Directory.

Situation: the request is at NPS. Action: three check rows light in order — connection policy, network policy, identity in AD — while a route is drawn from the directory into NPS. Consequence: NPS is shown holding the combined result.

F17 · The verdict6.6s

Then it answers. Access-Accept opens the port. Access-Reject leaves the device with no network access at all.

Situation: NPS has finished the checks. Action: an ACCESS-REJECT reply reaches the switch and leaves its port closed; an ACCESS-ACCEPT reply follows the same route and opens it. Consequence: the switch port visibly changes to the accepted state.

F18 · And then the normal path8.6s

Once the port opens, everything you already saw happens next. DHCP, then DNS, then the domain controller.

Situation: the port is open. Action: two tokens replay the chain in order through the already-established routes. Consequence: a green DC NEXT closes the ordered replay.

F19 · NPS is conditional11.3s

On a network without 802.1X, NPS never appears in this flow. DHCP and DNS take the device straight to the domain.

Situation: the same devices, no policy gate. Action: the open port is emphasised, DHCP lights first, and NPS is dimmed out of the flow. Consequence: an explicit contrast with the previous scene, with NPS visible but unused.

F20 · The complete flow11.3s

Put it together. Authenticate at the port, get your settings from DHCP, find the domain in DNS, and sign in at the domain controller.

Situation: every part has been taught. Action: one sequence of four numbered steps lights in order while the identity token runs the chain. Consequence: the whole flow is on screen in order, still on the two-column stage.

F21 · The takeaway11.7s

Four services, four jobs. NPS decides access. DHCP configures the network. DNS finds the domain. The domain controller handles identity and domain services.

Situation: the flow is complete. Action: the four services are shown together and each is lit as its job is spoken. Consequence: a four-way comparison with no new concept introduced.
